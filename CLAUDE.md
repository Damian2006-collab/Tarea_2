# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Dami's Burguer — a static multi-page marketing site for a burger restaurant, built incrementally without a frontend framework or bundler. TypeScript is used only for future form-validation logic, not for the page structure itself.

## Commands

- `npm run build` — compiles `ts/**/*.ts` to `js/` via `tsc`. Fails with `TS18003: No inputs were found` until at least one `.ts` file exists in `ts/`.
- No dev server script is defined. Serve the static files with any static server (e.g. `python -m http.server 8000`) and open the HTML files directly — no build step is required to view any page.
- No lint or test commands are configured. The `test` script in `package.json` is the default npm placeholder, not a real test runner.
- `dist/` is a generated deployable copy, not a build the tooling produces automatically — regenerate it by running `npm run build` then copying the six `*.html` files, `robots.txt`, `css/*.css`, and `js/*.js` into `dist/` (skip `ts/`, `node_modules/`, `package*.json`, `tsconfig.json`, `.claude/`, and the `.md` docs — those aren't needed to serve the site). It's gitignored; Netlify currently deploys straight from the repo root (publish directory `.`), so `dist/` isn't wired into the live deploy — it exists for anyone who wants a standalone folder to drag-and-drop deploy or serve elsewhere.

## Architecture

**Pages are self-contained HTML files, not templated, but CSS is centralized.** `index.html`, `menu.html`, `nosotros.html`, `login.html`, and `registro.html` each `<link rel="stylesheet" href="css/styles.css">` in `<head>` — all styling (colors, spacing tokens in `:root`, header/nav rules, responsive breakpoints, `.auth-card`/`.auth-form` rules, etc.) lives in the single `/css/styles.css` file. Edit it once; every page picks up the change. (This replaced an earlier per-page-duplicated `<style>` block — if you see stray inline `<style>` in a page, it's a regression, not the convention.)

**Site structure and nav:**
- `index.html` is the home page and owns the sections that don't warrant their own page: hero (`#inicio`), a featured-menu preview (`#menu`), `#nosotros` and `#testimonios` anchors, and the `#contacto` section containing the live contact form.
- `menu.html` is the full catalog: five `.menu-category` groups (Clásicas, BBQ, Veggie, Acompañamientos, Bebidas) of `.menu-card`s, each with a quantity stepper (`.qty-btn--minus`/`.qty-input`/`.qty-btn--plus`) and an "Agregar al pedido" button (`.btn--add-to-cart`, carrying `data-item-id`/`data-item-name`/`data-item-price`), plus a `#tu-pedido` cart summary section driven by `ts/carrito.ts`.
- `nosotros.html` is the full brand page: historia (`.two-columns` with `.about-image`), values (`.value-grid` of `.value-card`), and team (`.team-grid` of `.team-card`).
- `login.html` and `registro.html` are complete auth pages — each has a centered `.auth-card` with a form and a full `<footer>`. They cross-link to each other via `.auth-switch`. Only `login.html` has a top-level nav entry ("Iniciar sesión"); `registro.html` is reached from the login page's switch link, not from the main nav.
- Cross-page nav links use relative paths (`menu.html`, `nosotros.html`, `login.html`) for dedicated pages and `index.html#anchor` for sections that only exist on the home page. Each page's own nav item carries `aria-current="page"`. `index.html` also cross-links forward into the two dedicated pages: a "Ver menú completo" button under the featured-menu preview, and a "Conoce nuestra historia completa →" `.inline-link` under the `#nosotros` blurb.
- Every page duplicates the same inline nav-toggle/`Escape`-to-close `<script>` at the end of `<body>` since there's no shared JS include yet. Every page now has `.animate-on-scroll` content, so all five duplicate the `IntersectionObserver` block in that same script.

**Forms:** each form follows the same contract — a semantic class hook plus a `<div class="form-feedback"></div>` immediately after `</form>` — for upcoming TypeScript validation:
- Contact (`index.html#contacto`): `<form class="contact-form form-contacto">` with `#nombre`, `#email`, `#mensaje`.
- Login (`login.html`): `<form class="auth-form form-login">` with `#email`, `#password`.
- Registro (`registro.html`): `<form class="auth-form form-registro">` with `#nombre`, `#email`, `#password`, `#confirmar-password`.

Keep these class/id contracts stable — they're the hooks the TS validation scripts query against.

Each field carries `aria-describedby` pointing at a `<span class="field-error" id="error-*" aria-live="polite">` (combined with the existing `#hint-*` id where a hint paragraph is also present) plus `aria-invalid="false"`. The validation scripts toggle `aria-invalid` and set the error span's text at submit time — they never inject new DOM nodes, only fill in elements that already exist in the markup. `.form-feedback` gets a `form-feedback--success`/`form-feedback--error` class and a summary message; `.field-error:empty` collapses visually via the `min-height` in CSS rather than `display:none`, so screen readers still get a stable live region.

**Dark mode:** every page supports a manual light/dark toggle (`#btn-theme`, the 🌙/☀️ button next to the logo), driven by a `data-theme="dark"|"light"` attribute on `<html>`. Two pieces make this work:
- A blocking inline `<script>` at the very top of `<head>` (before the stylesheet `<link>`), duplicated per page, reads `localStorage.getItem('theme')`, falls back to `prefers-color-scheme`, and sets `data-theme` before first paint to avoid a flash of the wrong theme.
- A `[data-theme="dark"]` block right after `:root` in `css/styles.css` (single copy, applies to all pages) that overrides the color tokens plus a few hardcoded selectors that don't use CSS variables (`.site-header`, `.site-footer`, card backgrounds, form inputs).

The toggle click handler (bottom `<script>`, still duplicated per page since there's no shared JS include) flips the attribute and persists the choice to `localStorage`, so the preference carries across pages on the same origin.

**Mobile-first CSS:** unqualified rules in `css/styles.css` are the mobile layout (single-column grids, centered hero, collapsed `.main-nav` dropdown, visible `.nav-toggle`); a single `@media (min-width: 769px)` block near the end of the file progressively re-enables the desktop layout (two-column grids, static horizontal nav, hidden toggle). There is no `max-width` breakpoint and no `!important` — desktop overrides win purely through source order (declared after the base rules, same specificity). If you add a new responsive rule, follow this pattern: write the mobile behavior unqualified, then add the desktop override inside the existing `min-width: 769px` block.

**Typography tokens:** `:root` also carries `--font-family-base`, `--font-size-sm/base/md/lg`, `--font-size-section-title`, `--font-size-hero-title`, and `--line-height-base`. `body`, `.logo`, `.section-header h2`, and `.hero h1` consume these; other font-sizes in the file (menu cards, badges, form hints, etc.) are still literal values — extend the token set if those need to become swappable too.

**SEO:** `robots.txt` at the project root allows all crawlers (`User-agent: * / Allow: /`) — there's no sitemap since the project has no deployed domain yet. Each page's `<head>` carries Open Graph (`og:type`, `og:title`, `og:description`, `og:image`) and Twitter Card (`twitter:card=summary_large_image`, `twitter:title`, `twitter:description`, `twitter:image`) meta tags mirroring that page's own `<title>`/`<meta name="description">`. All five pages currently reuse the same hero photo as `og:image`/`twitter:image` since no page has a more specific dedicated image asset.

**TypeScript pipeline:** `tsconfig.json` compiles `./ts` → `./js` with `target`/`module: ES2022`, `lib: ["ES2022", "DOM"]`, and `strict: true`. `/ts` and `/js` are in use:
- `ts/contacto.ts` → `js/contacto.js`, loaded only by `index.html`, validates `.form-contacto`.
- `ts/login.ts` → `js/login.js`, loaded only by `login.html`, validates `.form-login`.
- `ts/registro.ts` → `js/registro.js`, loaded only by `registro.html`, validates `.form-registro` (includes password length + confirm-password match).
- `ts/carrito.ts` → `js/carrito.js`, loaded only by `menu.html`. Wires the quantity steppers and "Agregar al pedido" buttons on every `.menu-card`, and renders the `#tu-pedido` cart summary. Cart state is a `CartItem[]` persisted to `localStorage` under `damisburguer_carrito` — this is a simulated order flow (per `PLAN.md`), no backend involved. Unlike the form validators, `renderCart()` *does* create DOM nodes dynamically (`document.createElement` for each `.cart-summary__item`), since the cart list has a variable number of rows — this is an intentional, documented exception to the "never inject new DOM nodes" convention the form scripts follow.

None of these files use `import`/`export` — each is a self-contained IIFE compiled as a plain script (not an ES module), so it's loaded with a plain `<script src="js/*.js"></script>` at the end of `<body>`, no `type="module"` needed. Each form-validation script locates its form via `document.querySelector('.form-*')`, and its feedback element via `form.nextElementSibling` (relying on `.form-feedback` being the form's immediate next sibling in the markup — don't move it elsewhere without updating the script). Logic is duplicated per file rather than shared via an import, consistent with the rest of the project's per-page duplication convention.

**Images:** every photo on the site is an Unsplash URL (`https://images.unsplash.com/photo-<id>?w=…&h=…&fit=crop&q=80`) — there's no local `/img` asset folder. Unsplash photo IDs can 404 (one already did — the original hero photo was removed upstream). Before adding or reusing a photo ID, verify it resolves with `curl -s -o /dev/null -w "%{http_code}" "<url>"` and expect `200`; don't assume an ID is valid just because it looks like a real Unsplash slug.

**`playground.html` is a separate backoffice component library, not part of the public site.** It has its own aside-nav + six `<section>`s (Alerts, Botones, Checkboxes/Radios, Dialogs, Menús, Toasts) showing the real markup for each interaction pattern, with a second column per section documenting keyboard/focus behavior. It intentionally does **not** share `css/styles.css`, the header/nav, or dark mode with the rest of the site — it links only `css/playground.css`, which is a pure `@import` aggregator (in this order: `variables.css`, `alerts.css`, `botones.css`, `checkboxes-radios.css`, `dialogs.css`, `menus.css`, `toasts.css`). `variables.css` holds shared semantic color tokens (`--semantic-error/success/warning/info`) meant to be reused across components (e.g. `.c-alert--error` and a future `.c-toast--error` both referencing `--semantic-error`) — add a new shared token here, not inside a single component file. The six component files only define selectors for the `c-*` classes used in `playground.html` plus two empty `@media` breakpoints (`768px`, `480px`); as of this writing only `alerts.css` has real properties filled in (added by hand, not by Claude) — `botones.css`, `checkboxes-radios.css`, `dialogs.css`, `menus.css`, and `toasts.css` are still empty shells. Don't fill any of them in unless asked, and if you do add properties to a component file, put shared tokens in `variables.css` rather than redeclaring them locally. Behavior (opening/closing the `<dialog>` with `.showModal()`, the two `.c-menu-account-toggle` dropdowns, and the auto-dismissing `.c-toast` queue capped at 3) lives in `ts/playground.ts` → `js/playground.js`, same no-import/plain-`<script src>` convention as the rest of `/ts`.
